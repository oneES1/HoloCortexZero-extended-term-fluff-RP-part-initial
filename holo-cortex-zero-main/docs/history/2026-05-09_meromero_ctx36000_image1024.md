# MeroMero 本地多模态上下文与图片压缩调整（2026-05-09）

## 背景

用户反馈 Gemma/MeroMero 本地多模态 OCR 效果偏弱，排查确认 `local_chat_image_max_long_edge=768` 为等比缩放而非裁剪，但会降低截图/小字 OCR 可读性。用户要求：

- 保持 `-np 2` 双槽。
- 将总上下文改为 `36000`，目标单槽约 `18000`。
- 将本地图片长边压缩阈值从 `768` 放宽到 `1024`。
- 保持当前 `IMAGE_MAX_COUNT=3` 三图限制。

## 修改内容

### hcz 远端 llama-server 服务

文件：`/path/to/systemd-user/meromero-gguf.service.d/10-runtime.conf`

修改后：

```ini
[Service]
Environment=MEROMERO_CTX=36352
Environment=MEROMERO_PARALLEL=2
Environment=MEROMERO_BATCH=384
Environment=MEROMERO_UBATCH=384
```

生效命令：

```bash
systemctl --user daemon-reload
systemctl --user restart meromero-gguf.service
```

运行态证据：

```text
llama-server ... -c 36352 -b 384 -ub 384 -np 2 ...
health=200
```

直连 1 次请求后的日志证据：

```text
slot update_slots: id  1 | task 0 | new prompt, n_ctx_slot = 18176, n_keep = 0, task.n_tokens = 19
prompt eval time = 135.85 ms / 19 tokens
eval time = 908.91 ms / 37 tokens
```

说明：`MEROMERO_CTX=36352`、`MEROMERO_PARALLEL=2` 下，llama-server 实际槽长日志为 `18176`，接近目标单槽 `18000`，存在服务端对齐。


### 防自恢复覆盖修正

远端存在启动脚本默认值与 systemd drop-in 两层来源。为避免服务自恢复/重启时被脚本默认值覆盖，已同时修改：

- `/path/to/services/qwen35_stack/run/start_meromero_gguf.sh`：`CTX=${MEROMERO_CTX:-36352}`
- `/path/to/systemd-user/meromero-gguf.service.d/10-runtime.conf`：`Environment=MEROMERO_CTX=36352`

验证命令显示运行进程为：

```text
llama-server ... -c 36352 -b 384 -ub 384 -np 2 ...
```

再次请求后的槽长证据：

```text
slot update_slots: id  1 | task 0 | new prompt, n_ctx_slot = 18176, n_keep = 0, task.n_tokens = 19
```

## 风险与回滚

风险：

- `1024` 长边会比 `768` 增加视觉处理显存和图片 token 压力，但当前保留 `IMAGE_MAX_COUNT=3`，且总上下文从 `38912` 降到 `36000` 给显存留出空间。
- `-np 2` 仍会双槽占用 KV cache，图片请求高峰时仍需观察 OOM 是否消失。

回滚点：

- 远端 service drop-in 已自动备份为 `10-runtime.conf.bak_*`。
- 本地 YAML 已自动备份为 `holo-cortex-zero.yaml.bak_*`。
- 可回滚为：`MEROMERO_CTX=38912`、`local_chat_image_max_long_edge=768`，然后分别重启远端服务与 HCZ 容器。
