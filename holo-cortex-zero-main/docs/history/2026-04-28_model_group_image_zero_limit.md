# 2026-04-28 模型组图片 0 上限语义修正

## 背景

模型组配置中的 `IMAGE_MAX_COUNT` 原先使用 `0` 表示“不限”，导致无多模态模型无法通过配置表达“不要向模型发送任何图片”。用户在模型组里填写 `0` 时，实际链路会跳过图片限额处理，图片仍会进入 chat / responses / gemini 发射器，容易触发无 vision 能力模型的协议或供应商报错。

## 当前主链

- `ModelConfigGroup.IMAGE_MAX_COUNT` 提供模型组级图片数量策略。
- `run_agent_v2._build_model_group_extra_params` 将模型组字段写入内部参数 `__hcz_image_max_count`。
- `llm.router` 在协议发射器前统一执行图片数量裁剪、图片物料化和兼容归一化。
- chat / responses / gemini 发射器只负责各自 wire format 序列化，不承担模型组图片限额判断。

## 修改

- 将 `IMAGE_MAX_COUNT` 语义改为：
  - 留空 / `null`：不限图片数量。
  - `0`：不向模型发送 user 图片，所有 user 图片统一降级为文本占位。
  - 正整数：最多向模型发送该数量的 user 图片。
- 正整数限额继续沿用原策略：内置系统形象参考图优先保留，普通图片按从旧到新降级。
- `0` 禁图时不再保护系统形象参考图，避免无多模态模型仍收到 protected image。
- 前端模型组配置页同步改为留空表示不限，填 `0` 表示禁用图片。
- 中英文配置文案同步更新，避免继续误导为 `0` 不限。

## 影响范围

- 通用模型组媒体策略改变，不针对任何供应商或模型名称做特化。
- 只影响新架构 LLM router 主链进入协议发射器前的 user 图片处理。
- 音频、视频、tool 结果、多模态正则路由、协议选择逻辑不在本次修改范围内。

## 回滚点

如需恢复旧语义，可回退本次提交；旧行为是 `IMAGE_MAX_COUNT=0` 表示不限，禁图无法通过该字段直接表达。
